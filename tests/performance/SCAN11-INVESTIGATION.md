# Sustained scanner investigation — proposals only

September 11, 2026: the owner reports SCAN-10 now works on their phone. They also report camera shutdown after 50 cards, immediate shutdown on restart, and a very hot phone. The new target is thousands of cards over hours. SCAN-11–14 authorize investigation and proposals; no performance implementation or deployment is included here. The inspected `public/` tree exactly matches published r125-a2 commit `79c0ced9ca188d483a221d80b9dc67f79c536ce3`. This is static code inspection, not a CPU, memory or thermal measurement.

## Concrete findings

- **The restart failure follows the deliberate cap.** [`enqueue`](../../public/scanner.js) stops at 50 accepted/queued/processing rows or 150 attempts. `start()` preserves rows and attempts, so the next admitted frame stops again. Only `open()` resets them. The independent provider's separate 50-call limit falls back to primary recognition; it does not stop the camera. This explains the report without establishing whether the phone also throttled or experienced another failure.
- **Continuous analysis remains expensive between reads.** `tick()` targets 120 ms (about 8.3 Hz when work fits). Each tick creates a guide canvas, with a four-million-pixel ceiling, plus 24×32 signature and 96×128 quality canvases/readbacks. [`camera.js`](../../public/camera.js) requests ideal 2560×1440 with no explicit frame-rate constraint. Actual device settings vary. Four million RGBA pixels represent 16 MB of raw pixel storage, an upper-bound calculation rather than measured allocation. The burst retains at most three frames, and checked/in-flight frames can retain additional canvases.
- **Geometry runs whenever its worker becomes free**, even during recognition and the one-second post-read interval. [`card-regions.js`](../../public/card-regions.js) normally runs Cornelius twice at 384×384, including a copied masked frame to detect additional cards. The separate [`visual-worker.js`](../../public/visual-worker.js) runs Cornelius again and Milo at 448×448. Both workers use WASM with one inference thread each; being off the UI thread does not make their work free. This duplicate detector/model residency is an optimization candidate, not a measured dominant cost.
- **Stationary duplicates still incur recognition.** Oracle-ID suppression happens after recognition resolves. Continued stable input can therefore run full local/cloud recognition repeatedly. A local read can perform one to six embeddings with rotation/light variants. [`visual-search.js`](../../public/visual-search.js) scans 112,049 catalog rows ×128 dimensions per embedding: about 14.3 million scalar products; packed float16 embeddings alone are 28,684,544 bytes, excluding records, models and runtime heaps. These are code/manifest-derived sizes, not total resident memory. Each cloud adapter separately encodes JPEG/base64; up to primary and independent requests can accompany the local read.
- **Cleanup is partly good, partly worth tightening.** Inference tensors are disposed in `finally`; frame pixels transfer to workers; hydration caches are capped at 100 entries; queued/burst frames are bounded. Stop aborts requests, stops camera tracks and clears the burst/queue. Review/background/sign-out dispose recognition workers. A plain cap stop does not explicitly dispose an already-idle visual worker; the overlay's `clear()` leaves its animation-frame loop running until `destroy()`. This is retained work/resources, not proof of an accumulating leak.
- **Persistence and rendering do not scale to thousands as written.** Each scanner `update()` rebuilds the entire text wheel and calls `onRows`. [`scan-import.js`](../../public/scan-import.js) clones the full batch, synchronously serializes it into localStorage, and serializes a full IndexedDB write (opening/closing the database per write). Accepted captures, late provider updates, controls and unresolved nonduplicate attempts can trigger this; suppressed duplicates do not. Captured images are not journaled. Cloud staging occurs on Review/Back handoff, not on every accepted camera result. The 50-row cap currently bounds this cost; lifting it alone would make memory, writes and DOM work grow.

## Prioritized paths for implementation approval

1. **Design continuous bounded storage first.** Use a durable scan-session identifier, immutable capture IDs and ordering, an incremental local outbox, and transparent bounded server staging batches. Keep only a recent window and bounded in-flight images in memory; page older pending items and virtualize review. Preserve retry idempotency, reload recovery, late updates on the original capture, explicit later Add, and the last accepted Oracle ID across internal rollover. Retain safe transaction/request bounds without a fixed total-session camera stop. Network/storage backpressure must be visible and recoverable without dropping captures or growing RAM indefinitely.
2. **Give analysis a continuous resource budget.** Reuse small analysis buffers; create a high-resolution recognition frame only when a read is due. Rate-limit geometry independently and avoid full-rate checks during recognition/cooldown, while ensuring every admitted capture has valid fresh single-card evidence. Use bounded adaptive retry/backoff for repeated accepted identities or unclear reads; periodically recheck so a new card cannot get stuck behind a visual-change latch. Keep SCAN-10 acceptance authoritative. Update overlays only for changed state/active animation and pause the draw loop when stopped. Measure candidate camera resolution/frame-rate limits against recognition quality before choosing them.
3. **Then compare larger recognition tradeoffs.** Reuse validated geometry in local recognition, or serialize/shared-worker model execution to avoid duplicate detector residency. Compare a cloud-first mode with local fallback against the current parallel race; it can trade phone compute for latency, connectivity and provider cost. Do not assume switching to GPU/WebGPU, adding threads, disabling variants or lowering resolution improves sustained heat or accuracy without measurement. Share one encoded frame across remote consumers where appropriate.

## Proposed validation, not yet run

Start with short controlled active, stationary, unknown and paused workloads to count captures, geometry/model runs, frame bytes, persistence bytes, worker lifetime and latency. Then target **at least 2,000 accepted captures over at least two hours** as an initial engineering benchmark, not promised throughput or a new cap. Require a memory plateau independent of total captured count, bounded pending work, stable responsiveness, correct A,A / A,B,A across batch boundaries, ordering and reload recovery after network/storage interruptions. Test explicit ownership confirmation separately. Repeat on the owner's physical phone and record heat/battery observations and actual camera settings before claiming thermal improvement. No broad tests, image replay, model calls or deployment were performed for this investigation.
