## Replace a model

RecognitionService accepts plain visual.inspect(image) and ocr.read(image,corners) ports with version metadata. Only composition.py imports concrete adapters. A replacement adapter translates its evidence into the common policy; it does not modify browser behavior. Visual and text adapters can be replaced independently. Configuration chooses KEEPER_VISUAL_ADAPTER and KEEPER_OCR_ADAPTER; unsupported names fail initialization. There is no user-facing model selector or dynamic plugin loader.

Results contain contractVersion, confirmed/possible/unknown status, candidates, selected, reason, evidence, versions and timings. Cosine similarities and distances are not probabilities. Each adapter owns its calibrated interpretation; swapping weights, catalog, preprocessing or OCR requires new version-specific calibration. Models and catalog must be replaced atomically. Runtime never refreshes or downloads artifacts. There is no image/result cache. A visual failure becomes unknown; a strong visual identity with unavailable OCR remains an optional candidate only. Service unavailability is shown as retry; there is no silent fallback that changes confidence meaning.

Production composition hard-disables confirmed results. The research thresholds only filter optional candidates. The browser also rejects automatic confirmations until real-frame calibration and a reviewed activation change. Final explicit ownership confirmation remains mandatory.

## Build and verify

Use Python 3.12 on Linux, pip install -r recognition/requirements-linux.txt, then python recognition/scripts/prepare.py. This fetches only public frozen files and verifies their hashes. In a separate Linux Python environment install requirements-converter.txt and run recognition/scripts/convert_ocr.py. It exports the original frozen text weights to ONNX and records original/output hashes and the Latin dictionary. The converter's Paddle runtime is build-only. Run PYTHONPATH=recognition python -m unittest discover -s recognition/tests -v and node --test tests/backend-recognition.test.js. Stage/commit source before python recognition/scripts/source_bundle.py, then docker build -t keeper-recognition recognition. Run the image with --network none --read-only --tmpfs /tmp:rw,size=512m --entrypoint python and smoke.py. The branch's read-only CI workflow performs these checks without AWS credentials or owner images. Container checks and synthetic frames do not establish physical camera accuracy.

The cloud default is paddle-onnx: original PP-OCRv5 mobile/Latin weights, RapidOCR 3.9.2 preprocessing and ONNX Runtime CPU sessions. Only the explicit detector, recognizer and Latin dictionary are loaded. There is no default-model, orientation or font download. The original paddle adapter remains selectable in an environment containing its dependencies from requirements.in; it is deliberately absent from the slim cloud image. Converted preprocessing has its own unapproved calibration version. Both choices remain possible/unknown only. This runtime repair addresses observed cold-start failures in the original Paddle image; successful fresh AWS initialization must be established separately.

ORT_DISABLE_TELEMETRY=1 is enforced before adapter imports and supplied by Docker and CloudFormation. ONNX Runtime 1.29 initializes a native POSIX telemetry uploader/device identifier before its Python disable_telemetry_events API can be called; that API alone suppresses only non-essential events. The full early opt-out is required by this service's no-runtime-network design. See the pinned [upstream privacy instructions](https://github.com/microsoft/onnxruntime/blob/v1.29.0/docs/Privacy.md). Native network activity cannot be detected by patching Python socket.connect alone, so offline smoke checks do not establish this property by themselves. Initial cold file reads can still be slower than CI; actual AWS fresh-runtime results remain the activation gate.

lambda_entry.py imports libraries during Lambda's normal on-demand INIT phase; it does not construct models or issue a preparation request. Model construction remains lazy, after authentication and image validation. The function keeps its 20-second invocation limit. The new route waits up to 29 seconds and the scanner up to 35 seconds so normal INIT time is not mistaken for a failed invocation. Numeric startup phases distinguish import, visual-model and OCR-model loading without recording request data. There is no provisioned instance, keepalive, scheduled preparation, or dependency on a previously used process.

requirements-linux.txt fixes all resolved Python dependency versions; Dockerfile fixes the Lambda base digest and installs the required OpenCV/OpenMP system libraries. requirements.in records the original direct requirements. Runtime memory, initialization and per-frame timings are reported separately. No GPU acceleration is claimed. Actual AWS and browser measurements are retained in tests/performance/EVIDENCE.md.
